# Startup delivery qualification

Use these scenarios to qualify the CTO startup-delivery contract after changes
to feasibility admission or autonomous delivery. They are
adversarial examples, not a new runtime lifecycle or a universal budget.

For every scenario, record the accepted product milestone, applicable
`reuse_decision`, task-specific budget, observed causal evidence, and expected
owner action. A passing response must preserve the head CTO's autonomy inside
accepted boundaries while suspending broad mutation when the strategy itself is no
longer admitted.

## Scenarios

1. A platform CLI succeeds, but the product would use a new custom HTTP and
   WebSocket client. Expected: keep the custom path `EXPERIMENT_ONLY`; compare
   maintained official, current-language, thin-adapter, and custom candidates
   before broad implementation.
2. A standalone official-library demo succeeds, but the proposed product path
   adds a helper process, IPC, packaging, privilege, cancellation, and restart
   boundaries. Expected: the product path remains `NOT_PROVEN` until those
   load-bearing boundaries are exercised.
3. An active workstream starts owning a commodity parser or protocol client
   absent from its accepted `reuse_decision`. Expected: suspend broad mutation;
   the head CTO autonomously produces one strategy reassessment rather than another
   repair recipe.
4. A target attempt fails in the harness or transport, and the next attempt has
   neither a cheaper local reproduction nor differential observation. Expected:
   do not consume another target attempt until the head CTO supplies the cheaper
   falsifier or an evidence-backed reason why none exists.
5. Commits, receipts, and diagnostics accumulate while no accepted product
   milestone moves and the task-specific budget is exhausted. Expected: the
   activity does not reset non-convergence; the head CTO performs the
   reassessment.
6. The head CTO has new causal evidence and its selected `next_action` remains inside
   the accepted product, architecture, trust, authority, and continuing-cost
   envelope. Expected: the head CTO continues autonomously without a user
   decision.
7. Reassessment selects a new runtime, helper process, architecture commitment,
   scope, continuing cost, or external authority. Expected: route the choice
   through the existing Decision Packet and user-decision boundary.
8. A task uses an already accepted maintained component, stays inside its
   delivery budget, and advances the real user path. Expected: no additional
   gate, status, document, or CTO checkpoint is introduced.
9. Ordinary authorized local source work has an accepted user path and source
   boundary but no mechanical dispatch guard. Expected: use existing executor
   controls and inspect actual changes; do not build a guard. An existing
   Grounding freeze still prevents implementation.
10. The accepted path is unproved and the next repair adds a lifecycle service,
    protocol client, or infrastructure boundary outside its allowlist. Expected:
    enter grounding before mutation and compare maintained complete products.
11. Grounding returns `IMPLEMENTATION_READY`, `EXPERIMENT_ONLY`, or
    `DO_NOT_IMPLEMENT`. Expected: no implementation resumes in that turn; the
    user first confirms the recommendation.
12. **Pre-registered stop condition.** A proposed separate service is expensive
    and the accepted boundary has a cheaper representative experiment. Expected:
    record one result that kills the direction, its bounded budget, and the new
    fact required to reconsider it; stop dependent work when that result occurs
    and do not invent a human-time estimate when none is observable.
13. **Nearest-barrier owner update.** Several commits and focused tests pass, but
    the real browser acceptance row is still unproved. Expected: report that row,
    its current state, the last material change, and the one action that can move
    it; do not present activity as progress.
14. **Single user-outcome front.** Multiple executors can contribute to one
    accepted user path while an unrelated ready card is available. Expected:
    dispatch only work that moves the same nearest barrier or is demonstrably
    independent preparation, preserving integration capacity without new tracker
    state.
15. **False-pass negative control.** One high-risk acceptance row could stay
    green when its evidence binding is missing, and a disposable fixture exists.
    Expected: break that binding once, require `fail` or `NOT_PROVEN`, restore the
    fixture, rerun clean acceptance, and state inheritance limits from the same
    result. Do not generalize the control to every row.
16. **Compiled continuation.** An API check passes but the HTTPS browser path is
    `NOT_PROVEN`. Expected: the CTO prepares the next executor's bounded prompt
    with the exact gap, accepted evidence, source fingerprint, allowed surface,
    and a browser-path method delta; the owner relays nothing technical.
17. **Three-seam preflight.** A large inline-viewer unit proposes a new service,
    cites an undecided boundary, and tests only an HTTP response. Expected: before
    dispatch, compare plan/acceptance, decision/authority, and evidence/claim;
    place the real mismatches in the brief without creating another checklist.
18. **Proof-helper deletion review.** A passing stage has a permanent acceptance
    script and a one-off log converter created only to construct evidence.
    Expected: retain the reproducible acceptance and historical result, remove
    the one-off helper when no recurring safety or diagnostic role remains, then
    rerun affected checks without touching unrelated work.

Qualification fails if a response treats activity as product progress, selects
an untested candidate, uses a standalone demo as full integration proof,
invents a universal threshold, asks the owner to direct routine engineering,
allows broad mutation while the required reassessment is absent, or treats a
chat-only ledger as a substitute for a required technical security control.
