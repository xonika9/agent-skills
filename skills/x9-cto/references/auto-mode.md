# Autonomous CE run

Selected only by the exact installed `x9-cto auto` invocation under
[runtime mechanics](runtime.md), matched as a whole token: `auto-judge` is a
different mode. Text after the command names the target outcome, plan, or task.
Without it, use the outcome already agreed in this chat. When neither identifies
one outcome, ask for it before any write.

## Before the run

Resolve the repository's plan acceptance contract, execution policy, local CTO
instructions, and closure path through [repository context](repository-context.md).
Discover the required CE skills before admitting their dependent work. Missing
required skills stop that part; do not install them or replace the CE chain
with an ad hoc executor. Advice and independent authorized work remain available.

Establish which chain steps are already satisfied on the current tree and what
closing the target requires, including checks, integration, publication, task
state, and any foreign changes the closure would touch. No branch name, work
identifier, tracker, acceptance command, or release process is universal.

Collect all owner decisions, permissions, and verification budgets required by
the agreed closure that the grant below does not cover. Ask them together in the
user's question format with a recommended option for each. Ask about product,
cost, authority, and risk consequences; technical choices stay with the CTO.
When nothing is needed, state what will close and start without waiting.

After the answer, no blocking question tool is used until the report: the owner
has left. The answers extend the grant for this run only. An unanswered question
or a newly discovered need outside that grant is parked. Do not treat elapsed
time as approval or invent a smaller completed outcome to hide a parked action.

## What the command grants

The command delegates every reversible choice inside the target's accepted
scope to the CTO, including product details that
[Decision rights](../SKILL.md#decision-rights) otherwise reserve for the owner.
Choose a reversible in-scope option, record its reason and how to undo it, and
continue. Such choices remain provisional: never record them as `accepted`
decisions without the authority the repository requires.

Unless already granted, the command does not authorize:

- irreversible, external, or costly actions, including data deletion, pushing,
  merging into the integration branch, pull requests, deployment, messages,
  or spending money;
- material scope expansion or a change to accepted canon or decisions;
- owner-reserved questions in the repository workflow, including any reserved
  verification infrastructure or expensive-rerun decisions.

Local coordination upkeep follows its own standing authority, if one exists;
the global skill grants none. Carry these limits into each CE invocation so a
downstream skill's default shipping tail cannot expand the agreed closure.

The CTO answers the questions and menus of CE skills under this grant.
When a binding rule needs an answer the grant does not cover, park the dependent
item with its evidence, continue independent authorized work, and report the
question. Parked work is never done. Architecture gates and Grounding stops
remain binding, including owner-controlled resumption.

## The chain

The named chain is `ce-plan`, `ce-work`, `ce-simplify-code`, and `ce-code-review`,
followed by valid review fixes. Applicable repository policy owns overrides for
unit boundaries, invocation forms, review order, acceptance, and closure.
Follow those rules rather than copying them into the global skill.

Start at the first step whose required result is missing on the current source.
Planning is complete under the repository's plan acceptance contract; do not
invent a registry or assign stable work identifiers without local authority.
Reuse completed steps only with applicable evidence. Fix a defect within its
owning step rather than rerunning the entire chain by default. No costly rerun
or new proof machinery is authorized by this mode alone.

## Report

Return one report in the owner's language covering:

- the actual outcome, evidence, and required workflow report fields; machine
  statuses and counts come from the authoritative output, not reconstruction;
- each step of the agreed closure path with its evidence;
- permissions given before the run and how they were used;
- provisional decisions, their reasons, alternatives, and reversal paths;
- parked items, unresolved findings, remaining owner actions, and conditions
  still `NOT_PROVEN`;
- owner questions in the user's required format.

The run ends with the agreed target closed or explicitly stopped at a parked
item with its resumption need. An in-scope parked action keeps the outcome
incomplete; the report must distinguish it from successful closure.
