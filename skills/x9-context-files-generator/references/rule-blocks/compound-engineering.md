## Compound Engineering

Shared rules from the `x9-context-files-generator` template. Edit only Local, which takes precedence; the rest is replaced when the template changes.

These rules bind every Compound Engineering executor that plans or implements a delivery stage and take precedence over skill defaults. The acceptance lead is the role Local names; when Local names none, it is the owner.

- Any work, including review, planning, and implementation, may use a model from another provider configured in this environment and give it the private-repository content the work needs, without separate confirmation. Inside T3 Code, launch such a worker through T3 `delegate_task`, not through a skill's own launcher such as `ce-work` cross-model execution, so the user can see and stop it in the app.
- Multi-model work (Bake-off candidates, oracle panels, cross-model review) uses only Claude and GPT families unless the user asks otherwise.
- Every stage plan's Verification Contract names one stage acceptance command and its machine-readable output, and marks each acceptance row as `blocking` or `hardening`. A row is `blocking` when the plan's Definition of Done, an accepted decision, or another source named in Local requires it. A row is `hardening` only when those owners explicitly allow it to remain non-blocking; fault injection alone does not make a row `hardening`. Unlabelled rows in an existing plan are `blocking`.
- Before a delivery-stage candidate receives a stable work ID in the work registry named in Local, `ce-plan` inventories the required outcomes, planning-time technical decisions, affected processes and stores, independent risk seams, one independently observable result, the smallest bounded acceptance boundary, and the likely atomic implementation-unit range. A preliminary forecast may authorize planning but gives no stable work ID.
- Assess depth against the accepted outcome under the smallest viable design that preserves every required behavior and boundary. Assess the proposed technical construction separately. Unit count, one language, one directory family, or claimed linear sequencing do not lower depth.
- When a proposed construction makes the plan `Deep` but a smaller conforming design keeps the required outcome `Lightweight` or `Standard`, reject the construction and replan the same unnumbered candidate. Do not split the product scope or create recursively suffixed child work solely because of construction-induced depth. New reusable proof machinery triggers a necessity check: remove it when no accepted requirement needs it; otherwise include it in the smallest viable design and reassess depth.
- For a delivery program being cut as one dependency graph, complete every candidate plan and resolve every planning-time inter-candidate contract before assigning the first stable work ID. The acceptance lead then verifies the whole graph and assigns its flat IDs in topological order in one decision. Record each work's contributions to historical acceptance gates and criteria; gates are not work containers or parent IDs. Preserve historical identifiers, never reuse them, and never create nested letter or decimal suffixes.
- If any required outcome remains `Deep` under the smallest viable design, stop before assigning any program ID and propose new unnumbered outcome boundaries for the acceptance lead's approval. A pure aggregate or closeout does not receive its own work ID: fold its thin acceptance boundary into the delivering work that closes the corresponding gate.
- The acceptance inventory names the smallest boundary that certifies the observable result and defaults to thin aggregation of existing checks. It does not by itself authorize a new evidence schema, DSL, validator, baseline-evolution mechanism, runner mode, proof store, or proof platform.
- Under `ce-work`, the preferred practice becomes a requirement: run every implementation unit in its own fresh subagent, run the checks named in the unit's `Verification` field, and commit the unit before starting the next. The final report lists each unit with its commit SHA. A multi-unit stage delivered as one commit is rejected at acceptance. A unit already satisfied without changes records its verification and the existing commit that supplies it instead of creating an empty commit.
- Acceptance results come only from the output file of the stage's acceptance script, run on a tree where `git status` reports no changes. The runner must reject a dirty starting tree and source changes during the run. Cite that file; any stated status or count must be derived from it, not reconstructed manually. Scripts run by hand may be listed as work performed, not as results.
- A narrowly scoped exception applies only when the owner explicitly approves an acceptance-lead closeout from retained stage outputs and focused primary evidence, and the owning plan and decision log record that amended contract. The acceptance lead records source applicability, unresolved conditions, and the decision separately. This is a closeout decision, not a newly executed stage acceptance; never fabricate or relabel machine statuses, counts, or reports.
- In a standalone `ce-work` run for a delivery stage, the stage acceptance script is the first stage-level quality check. Until every `blocking` row passes, keep implementing or use `ce-debug`; do not invoke `ce-simplify-code` or `ce-code-review`. This override also disables simplify-as-you-go and the post-fix simplify/review steps of any `ce-debug` run before that first passing acceptance. For a stage with a paid external action, first run the stage script without payment credentials: every free `blocking` row independent of the final disposable target must pass. Target checks tied to that same environment and the paid row stay `not_proven` until final acceptance. This free result permits the one simplify/review pass; every deferred free row must pass before the paid action.
- After the first passing acceptance, or the passing free portion of a paid stage as above, run the applicable stage-level `ce-simplify-code` pass no more than once. Commit any simplification, require a clean tree, then run one completed full `ce-code-review` and retain its `scope.head_sha` as the reviewed snapshot. A failed review invocation may be retried until it produces a completed receipt.
- While applying review findings, run every check named by the finding and every affected unit's `Verification` field. For a changed file owned by no unit, run the closest applicable layer check and record that mapping as a departure. Commit review-fix batches, then rerun the stage acceptance script on the clean final tree using the smallest acceptance scope allowed by the Verification Contract. Reuse a passing result only with its recorded command, source revision, and evidence that it still applies. A full rerun is not automatic: identify what remains unproven by retained evidence and affected checks, and ask the owner before an expensive repeat. If the accepted plan requires every check afresh, propose an explicit contract amendment before using earlier results; do not silently bypass the plan or construct a passing result. For a paid stage, rerun affected free checks after review fixes and perform the paid acceptance once on the clean reviewed tree. Any later change that affects its live proof requires a new admission; an unknown paid outcome is never retried automatically.
- Do not repeat the full review for ordinary finding fixes or acceptance reruns. If post-review work materially changes behavior, security, or architecture beyond the reviewed findings, return blocked for an acceptance-lead decision. When the acceptance lead requests another review, run only the delta with `base:<scope.head_sha from the first review>` and wait for its completed result.
- A finding showing that a `blocking` row cannot hold is not residual work: fix it or return blocked. Record every other justified unapplied finding under `Residual findings` in the final report with severity and `file:line`. List review-fix commits alongside implementation-unit commits.
- Shipping for a delivery stage ends at local commits on the stage branch: do not push, open or update a pull request, merge, babysit, or write to a tracker. This is the project-defined shipping process for standalone `ce-work` and an explicit `commit only` override for interactive `ce-debug` runs within the stage. Publication after acceptance follows Local; without a Local rule, the owner publishes after the acceptance lead accepts.
- When a rule cannot be followed as written, keep every check and every piece of evidence; among the options that do, choose the smaller change. Record the departure in a `Departures` section of the final report and continue only when no rule requires stopping. A departure cannot waive a plan- or canon-required input, a `blocking` acceptance row, a safety boundary, or an owner decision; return blocked when one of those cannot be satisfied.
